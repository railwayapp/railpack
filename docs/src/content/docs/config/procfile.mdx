Railpack detects a `Procfile` in the project root and uses it to set the
container start command. The file follows the
[Heroku Procfile](https://devcenter.heroku.com/articles/procfile#procfile-format)
format: one process type and command per line.

<Aside type="caution">
  Quotes in a command are kept and passed to the shell. A command that wraps
  the whole line in quotes, such as `web: 'python main.py'`, fails to start.
  See [Format](#format).
</Aside>

<Aside>
  Procfiles are deprecated and natively setting the start command with
  `RAILPACK_START_CMD` or in the `railpack.json` config file is recommended.
</Aside>

## Detection

Railpack will automatically detect a `Procfile` in your project root directory.
No additional configuration is required - if a `Procfile` exists, Railpack will
use it to set the container start command.

## Format

Each process is one line. The name before the first colon is the process type.
The rest of the line, after the colon and any following whitespace, is the
command. Quotes, colons, and `$PORT` stay in the command text.

```text title="Procfile"
web: gunicorn --bind 0.0.0.0:3333 main:app
worker: celery worker -A myapp.celery
scheduler: celery beat -A myapp.celery
```

Process type names may contain letters, digits, underscores, and dashes
(`web`, `background-job_1`). Blank lines and lines that start with `#` are
ignored. A line that does not match this pattern is skipped. When `web` or
`worker` is listed more than once, the last line of that type is used.

The start command runs as `/bin/bash -c`. Shell quoting inside the command
works. A colon in the command is fine, and quotes around a single argument
are shell syntax:

```text title="Procfile"
web: python -c "print('listening: 8080')"
```

```text title="Procfile"
web: "./bin/server" --port $PORT
```

Quoting the entire command makes the shell look up one program whose name
includes the spaces. `web: 'python main.py'` exits 127. Write
`web: python main.py`.

## Process Type Priority

Railpack prioritizes process types in the following order:

1. **web** - Highest priority, typically used for HTTP servers
2. **worker** - Second priority, typically used for background job processors
3. **Any other process type** - If neither `web` nor `worker` are defined,
   Railpack uses the first process in the file

This priority system ensures that web servers are preferred for containerized
deployments, while still supporting applications that only define worker
processes or custom process types like `scheduler`, `urgentWorker`, or `api`.

## Examples

### Web Application

```text title="Procfile"
web: node server.js
```

### Background Worker

```text title="Procfile"
worker: python worker.py
```

### Multiple Process Types

```text title="Procfile"
web: gunicorn app:application
worker: celery worker -A app.celery
scheduler: celery beat -A app.celery
```

In this example, Railpack will use the `web` command as the container start
command.

### Custom Process Types

```text title="Procfile"
api: ./bin/api-server
urgentWorker: python urgent_tasks.py
```

If no `web` or `worker` process types are defined, Railpack uses the first
process in the file (in this case, `api`).

## Integration with Other Configuration

The Procfile start command can be overridden by:

- Setting `RAILPACK_START_CMD` environment variable
- Defining `deploy.startCommand` in your [railpack.json config
  file](/config/file)

The priority order is:

1. `RAILPACK_START_CMD` environment variable (highest priority)
2. `deploy.startCommand` in railpack.json
3. Procfile process types (web → worker → other)
4. Provider-specific defaults (lowest priority)
